3 日々の進め方ヒント

  • 進捗の書き方: 「他の人が再現するのに役に立つ情報」を書く. 例えばビルドにしても, 日本語でこうしたああした, というレベルの情報ではなく, 打ち込んだコマンドラインをそのまま残す(貼り付ける)のが推奨. 特に, 公式サイトの指示では上手く行かなったような場合, 代わりにどうした, ということを「他の人はそれをコピペすればいい」レベルでそのまま書いておくことがよいです.
    • 他のメンバーの役に立つ
    • 後輩の役にも立つ
    • トラブル発生時に他の人が介入・ヘルプするのにも役に立つ(重要)
  • トラブル報告の仕方: 同じ理由で, トラブルに遭遇しているときも「やったことをありのまま書く」というのが大事です. 特に他の人に見てもらう場合,「ビルドしたけど◯◯がないとか言って上手く行きませんでしたがどうすればいいですか?」ではなく, 打ち込んだコマンドラインとシステムの出力, エラーメッセージなどをそのままベタッと(修正なく)貼り付けるのが重要です.
  • これはこの授業だけでなくオンラインコミュニティにヘルプを求める際にも重要な作法です. 「読んだ人が同じ現象を再現できるため」の情報, それも「最短時間で」再現できる(相手の時間を節約する)情報が重要で, それはすなわち, コピペすればいいだけのコマンドラインと, 起きることが同じかどうかを確かめられる出力, ということになります.
  • トラブルも進捗: 「こうやったけどこんなエラーになって困っている」というのも進捗です. 進捗報告に残したり, 最後のミニ発表でそれを見せるようにしましょう. 有用なヘルプをもらえる可能性が高まります.

4 AIおよびAI Codingについて

  • プログラミングにおいてAIは強力なツールになります
  • 普通のchat (ChatGPTやGemini) の対話で、
    • ツールやライブラリについて質問して解説してもらう
    • コマンドやエラーメッセージを貼り付けて原因究明・トラブルシュートをしてもらう というものの他に、coding agentと呼ばれるツールもあります
      • Claude Code, OpenAI Codex CLI, OpenCodeなどがあります
  • 普通のchatとcoding agentの大きな違いは、coding agentは、自分のPCにインストールして、ディレクトリをまるごと読ませる、ファイルを作らせる、コンパイルから実行まで多くの作業を代行させることができます. ソフトによって挙動の違いはありますが、テストまでやって失敗したらやり直す、できるまで続けるなど、大きな単位で仕事をさせることができます
  • 本演習でも、coding agentを使うとソースが含まれるディレクトリを丸ごと与えて
    • ファイル、ディレクトリの構成、どこでどんな機能が実装されているか説明させる
    • こんな機能を作りたいけどどのへんから見たら良いか説明させる などの使い方で、これまでよりも圧倒的に効率し、目指せる着地点が高まるものと思います
  • 本演習用AIとして以下を提供します
    • Open WebUI によるchat. ブラウザからg.ecc でサインインして使う
    • OpenCode による coding agent. 設定ファイルとAPI鍵を提供し、ツールは自分のマシンにインストールして使う

どちらも, モデルは様々なものを選択可能です - Coding agentの利用可能な範囲について - 上述した使い方の他、コードを実際に書かせるために使うこともできます（これが世間での良くある使い方）が、coding agentに何分〜何十分もかかる仕事をさせて結局何をしたのかもわからない、という使い方はしないこと - AIの能力を測るためにあえてやらせてみるという使い方はOKですが、それは自分たちの本題ではないところでやってください - AIに吐かせた、自分が見ていない行、チェックしていない行をを含んだコードをそのまま成果とすることは禁止です（つまり、書く部分は自分でやるものと思って下さい）

これには色々な理由があります

  • まず、大きなソフトの動きを理解する、理解して変更する、書き方を理解する、という身につけるべき力を身につける機会を失います
  • これを当然と思うならばこの先を読む必要はないですが、もしかすると、「そもそも『ソフトの動きを理解する、理解して変更する』のがこれからの時代に必要な力なのか」ということを疑う、あるいは不安を持つ人もいるかも知れません
  • ですがまずは表面的なこととして、多くのオープンソースのソフトウェア開発で、AI方針が定められています
    • LLVM
    • Fedora
    • QEMU
    • Rust (AI生成パッチに関する議論)
    • 多くのオープンソースプロジェクトの調査研究
  • 最終方針がどうあれ、共通した問題意識は「AIが生成したパッチをレビューし、取り込んでよいのかを判断する責任者（人間）の負荷」というところにあります。従って自分がきちんと理解せず、自分の言葉で説明できないようなパッチを、レビューアの負荷を考えずに送る、ということは慎まないといけないです
    • およそプロジェクトの責任からは程遠い見知らぬ人がAIでパッチを生成し、それをそのプロジェクトに責任を持つ少数のレビューアが、
      • 間違っていないか、
      • 別のところで問題が生じないか、
      • 将来的に維持できないコードにならないか、
      • ソフトウェア全体のコーディング規約、
      • 設計、考え方にそぐわないコードでないか、 などをレビューする、という負担のバランスが崩れているのが問題です
    • 「だったらレビューもAIを使えば?」と思うかも知れません。確かにレビューそのものもAIにやらせて人間のレビューアはろくにコードを見ずに取り込むか否かを判断すれば、表面的には負荷が減るでしょう。しかしすぐにわかる通りそれはAIを無条件に、盲目的に信じているのと変わりがありません
    • こう言うと「人間だっていつも間違えてるわけだしAIはきっと人間より優秀なんだから信じればいいじゃないか」と思う人もいるかも知れませんが、そのような思考を進めていったときに最終的に問題になるのは「責任」の問題でしょう。
    • AIコードでプロジェクトにクリティカルな問題が見つかった時「AIがやり、AIがレユーしてOKだったんだから仕方がない」とユーザ（人類？）全体が思うのであれば、それもありかも知れません（つまり、AIに支配される時代）。
    • でもおそらくほとんどの人はそうは考えないのではないでしょうか。おかしなことが起きたときに、それに責任を持つ「人」がいるから世の中が成り立っている、ということに気付かされます。AIに委ね、そこでAIが何をしても結果を受け入れる、という覚悟を人類全体が決めない限り、多くの人に使われているソフトウェア、ミッションクリティカルなシステムなど、システムに責任を持つ、そのための判断を専門的な知識に基づいて正しくできる人間、が不要になることはないでしょう
    • 世の中で、人間はコードを書かなくなる、というような予言をする会社（主にAIの会社）や人（主にAI会社のCEO）やがいました（誰が何を言い、それらの予言が当たっているかは自分で調べてみて下さい）。記事の見出しに踊らされないことが重要です
    • 上記の話からもわかる通り、「一人の人間がやるコーディングの大部分をAIがやれる」ということと、「ソフトウェアのチーム・コミュニティ開発がAIに置き換わり人間がほとんど不要になる」というのは別の次元の話だということかと思います
  • 個人的に共感を覚える最近見た動画を二つ紹介します
    • Linus Torvalds の対談 … ご存知 Linux 創始者、カーネル開発責任者（？）による対談。AIについて長く語っているわけではないですが、要は自分がパッチを受け入れる際にやっている仕事は「人に対する信頼」に基づいている、という意味のこと。
    • Charles Jones 教授 (スタンフォード、経済学) による講演（授業？） … どんな革命的な技術も急激な成長率の変化をもたらしているわけではない、という興味深いデータから始まり、技術が実際に社会に取り入れられて生産性の向上につながるまでには非常に時間がかかる、という趣旨の講演。上記の「一人の人間がやるコーディングの大部分をAIがやれる」ということと、「ソフトウェアのチーム・コミュニティ開発がAIに置き換わり人間がほとんど不要になる」というのは別の次元の話、ということとも通じるかと思います。
